# Generated taxonomy index

Generated by `npm run docs:generate` from `taxonomies/`. Do not edit by hand.

`scripts/validate-taxonomies.ts` checks that every declared location holds exactly the
full term set. A term set that is restated anywhere else fails validation, because a
restated enumeration is one waiting to drift.

## Artifact Types

Source: `taxonomies/artifact-types.yaml` — openness: **open** — consumers must handle unknown terms: `true`

The kinds of artifact Amasario can reason about. An artifact is any content- addressable or revision-addressable object that participates in provenance: it has an identity, it can be an input to or an output of a derivation, and it can carry evidence. Every artifact type declares whether a digest is required (`digestRequired`) and the digest algorithms permitted for it. A type whose identity cannot be established without a digest MUST NOT be represented by a revision string alone, because a revision can be rewritten while a digest cannot.

| Term | Label | Description |
| --- | --- | --- |
| SOURCE_ARCHIVE | source archive | A packaged snapshot of source code at a revision, such as a repository tarball at a commit. Digest-stable only when the packaging is itself reproducible, which is why the packaging method is recorded separately from the type. |
| LOCKFILE | lockfile | A resolved dependency manifest, such as Cargo.lock. This artifact is what converts declared dependencies into pinned ones, so it is the primary evidence for package dependency resolution. |
| BUILD_ARTIFACT | build artifact | The output of a build step before deployment, such as a compiled intermediate. May be produced by a build that is not reproducible, in which case reproducibility information MUST record that rather than being omitted. |
| WASM | wasm | A WebAssembly module, either the executable deployed to a network or an intermediate module. The identity of this artifact is its content hash, which is what a network reports; the artifact is distinct from both the contract address that hosts it and the source revision it was built from. |
| DEPLOYMENT_ARTIFACT | deployment artifact | The content actually submitted in a deployment, such as an uploaded WASM payload identified by the transaction that carried it. This type exists because the uploaded content and the resulting contract are two different objects, and conflating them hides the case where an upload was never instantiated as a contract. |

Enforced at: `schema/artifact.schema.json/properties/type`

## Change Types

Source: `taxonomies/change-types.yaml` — openness: **closed** — consumers must handle unknown terms: `false`

The exhaustive set of ways one snapshot or entity can differ from another. A diff entry MUST classify every difference with exactly one of these terms, and a diff MUST NOT report a difference caused only by non-deterministic ordering or by an unstable identifier.

| Term | Label | Description |
| --- | --- | --- |
| ADDED | added | The entity or relationship exists in the after-state and has no counterpart in the before-state. |
| REMOVED | removed | The entity or relationship existed in the before-state and has no counterpart in the after-state. |
| MODIFIED | modified | The entity exists in both states under the same identity and at least one non-identity property differs. Used when the change is not naturally described as an upgrade or downgrade, for example a change of evidence or of confidence. |
| UPGRADED | upgraded | The entity exists in both states and changed to a later version, revision or digest where the ordering is established by the referenced ecosystem (for example a package version or a monotonic ledger sequence). If ordering cannot be established, MODIFIED MUST be used instead: Amasario does not guess ordering. |
| DOWNGRADED | downgraded | The entity exists in both states and changed to an earlier version or revision under the same ordering requirement as UPGRADED. |
| REPLACED | replaced | The entity at a given identity changed to a different entity with no meaningful ordering relationship. The primary example is a contract whose deployed WASM hash changed, which is the change Amasario exists to make visible. |

Enforced at: `schema/impact.schema.json/properties/changeType`, `schema/diff.schema.json/properties/changes/items/properties/changeType`

## Confidence Levels

Source: `taxonomies/confidence-levels.yaml` — openness: **closed** — consumers must handle unknown terms: `false`

Confidences describe how strongly the available evidence supports a claim. They are an ordering, not a score: `ordinal` is the only comparison Amasario defines, and it exists so that aggregation across a multi-hop path is deterministic rather than dependent on implementation taste. A confidence level is never a substitute for evidence. Every claim at any level MUST reference the evidence that supports it; the level describes that evidence, it does not replace it. VERIFIED is therefore a statement about evidence completeness and consistency, never about trustworthiness or safety (see SECURITY.md).

| Term | Label | Description |
| --- | --- | --- |
| VERIFIED | verified | The claim is supported by complete evidence and the evidence is internally consistent, reproducible and independently checkable from the referenced records. If any evidence conflicts, the level MUST be lowered and the verification status MUST be CONFLICTING rather than VERIFIED. |
| HIGH_CONFIDENCE | high confidence | The claim is supported by authoritative evidence that is complete for the claim, but the evidence cannot be independently reproduced from the Amasario record alone (for example an issuer-signed attestation that Amasario can verify but not re-derive). |
| MEDIUM_CONFIDENCE | medium confidence | The claim is supported by evidence that is directionally correct but incomplete, for example a source revision matched by branch name rather than by exact commit digest. |
| LOW_CONFIDENCE | low confidence | The claim is supported only by indirect or circumstantial evidence, such as an interface shape that is consistent with a claimed dependency but does not establish it. LOW_CONFIDENCE findings MUST NOT be presented as established relationships in a report's observed-facts section. |
| UNKNOWN | unknown | No evidence supporting the claim is available, or the evidence available cannot be interpreted at this specification version. UNKNOWN means "not established", which is distinct from "established as false". |

Enforced at: `schema/confidence.schema.json/properties/level`

## Dependency Types

Source: `taxonomies/dependency-types.yaml` — openness: **open** — consumers must handle unknown terms: `true`

How a dependency relationship is classified. Classification answers *what kind of thing* is depended upon and *how the requirement was established*, so the type is a property of the evidence as much as of the entities involved. Each term declares `requiredEvidence`: the evidence types that must be present for a dependency of this class to be assertable at all. A dependency whose evidence does not satisfy its class MUST NOT be emitted; it may be emitted at a weaker class only if that class's evidence requirement is met. This is the mechanism that prevents Amasario from implying a dependency merely because two projects mention each other.

| Term | Label | Description |
| --- | --- | --- |
| DIRECT | direct dependency | The subject depends on the object through a relationship observed in the subject's own source, build configuration or deployment, with no intermediate entity. A direct dependency need not be a contract. |
| TRANSITIVE | transitive dependency | The subject reaches the object only through one or more intermediate entities, and the path is recorded on the dependency so that the reasoning can be reviewed. A transitive dependency MUST NOT be emitted without its path; an unexplained transitive edge is indistinguishable from a guess. |
| CONTRACT | contract dependency | The object is another Soroban contract. Established from an observed cross-contract invocation, or from an interface or address that the subject's source or storage demonstrably references. Interface similarity alone is not sufficient evidence. |
| PACKAGE | package dependency | The object is a software package or crate, established from a declared dependency in a manifest together with lock information where available. The declaration and the resolved version are distinct facts and MUST NOT be conflated. |
| WASM | wasm dependency | The object is a WASM artifact that the subject embeds, references or is derived from. Established from a matching digest or an explicit build input, never from size or metadata similarity. |
| RUNTIME | runtime dependency | The dependency exists only while the subject executes, for example a contract invoked during a transaction. Runtime dependencies are observable but not statically knowable, so they MUST be flagged as observed rather than inferred. |
| EXTERNAL | external dependency | The object is outside the observable Amasario boundary: a system, service or repository that Amasario can reference but cannot inspect or verify. The boundary MUST be stated on the relationship so that a consumer does not mistake a boundary for a verification failure. |

Enforced at: `schema/dependency.schema.json/properties/type`

## Deployment Statuses

Source: `taxonomies/deployment-statuses.yaml` — openness: **open** — consumers must handle unknown terms: `true`

What is known about a deployment event. A deployment status describes the current state of a record about a deployment, not a judgement about whether the deployment was a good idea. The statuses are ordered by how much is established: UNKNOWN carries no assertion, OBSERVED carries the assertion that a deployment record exists but not that it succeeded or is still effective, CONFIRMED adds success and effectiveness, and the remaining terms are explicit negative states.

| Term | Label | Description |
| --- | --- | --- |
| OBSERVED | observed | A deployment record was observed at the stated boundary, but its success or current effectiveness was not established. This is the honest default for a record discovered from a transaction that was not inspected in full. |
| CONFIRMED | confirmed | The deployment is evidenced as successful and the resulting contract is reported by the network at the stated boundary. Requires at least deployment and transaction evidence, and MUST NOT be asserted from a transaction that failed. |
| UNCONFIRMED | unconfirmed | A deployment was attempted or reported, but the resulting contract could not be observed. This differs from FAILED: the outcome is unknown rather than negative, and a consumer MUST NOT treat it as evidence of failure. |
| FAILED | failed | The deployment is evidenced as not having taken effect, for example because its transaction is recorded as unsuccessful. Only assertable from transaction evidence that explicitly records failure. |
| UNKNOWN | unknown | The status could not be established, for example because the deployment record was referenced but its transaction was not reachable at the observation boundary. Distinct from UNCONFIRMED, which means an attempt was observed. |

Enforced at: `schema/deployment.schema.json/properties/status`

## Evidence Types

Source: `taxonomies/evidence-types.yaml` — openness: **open** — consumers must handle unknown terms: `true`

The kinds of evidence Amasario can attach to a claim. Evidence is the only thing that makes a claim assertable, so every term declares where its records must be traceable to (`traceableTo`): the entity or record a reviewer would consult to independently confirm the evidence. Evidence is a record about a claim, never a property of an artifact. In particular an attestation is evidence about a claim made by an issuer, and must not be modelled as a flag on the thing attested to.

| Term | Label | Description |
| --- | --- | --- |
| SOURCE | source evidence | Evidence about a source repository, revision or source archive, such as a recorded commit digest or a repository reference. Traceable to the repository and the exact revision, not merely to the repository. |
| BUILD | build evidence | Evidence about how an artifact was produced: toolchain identity, configuration, target and lock information. Traceable to the build record and the inputs it declares. |
| ARTIFACT | artifact evidence | Evidence about an artifact's existence and identity, such as a computed digest. Traceable to the artifact bytes, since a digest is meaningless without the content it was computed over. |
| WASM | wasm evidence | Evidence about a deployed WebAssembly module's identity, such as the hash a network reports for a contract's executable. Traceable to the network observation that reported it. |
| DEPLOYMENT | deployment evidence | Evidence that an executable became a contract, such as the deployment transaction and the ledger it was included in. |
| TRANSACTION | transaction evidence | Evidence from a ledger transaction, such as its hash, inclusion ledger and success or failure outcome. A transaction that failed MUST NOT be cited as evidence that its intended effect occurred. |
| EVENT | event evidence | Evidence from a contract event emitted during execution. Events are the primary observable for cross-contract invocation, so this type is central to runtime dependency discovery. |
| ATTESTATION | attestation evidence | A signed or otherwise verifiable statement by an identified issuer about a subject. An attestation supports the specific claim it states and nothing broader; an attestation of a build MUST NOT be read as an attestation of contract behaviour or of safety. |
| OBSERVATION | observation evidence | A record that something was observed at a point in time, without asserting more than its presence. This is the weakest useful evidence and is what allows an honest statement that a boundary was reached rather than that a check failed. |

Enforced at: `schema/evidence.schema.json/properties/type`

## Impact Types

Source: `taxonomies/impact-types.yaml` — openness: **closed** — consumers must handle unknown terms: `false`

Classifications of a single impact finding. An impact record carries a non-empty set of these terms rather than exactly one, because a single finding is routinely several of them at once: a change reaching a contract three hops away is simultaneously TRANSITIVE, MULTI_HOP and CONTRACT. Three families exist and a finding MUST include at least one term from the `distance` family. The `distance` family is derived from `hopDepth` and is therefore mechanically checkable (see rule impact/direct-impact and impact/transitive-impact); the `entity` family classifies what was affected; the `trigger` family classifies the change that caused the finding.

| Term | Label | Description |
| --- | --- | --- |
| DIRECT | direct impact | The affected entity is reachable from the changed entity in exactly one hop. A finding whose hopDepth is 1 MUST include this term. |
| TRANSITIVE | transitive impact | The affected entity is reachable from the changed entity in two or more hops. A finding whose hopDepth is greater than 1 MUST include this term. |
| MULTI_HOP | multi-hop impact | The affected entity is reachable in three or more hops. This term is a refinement of TRANSITIVE and is used to distinguish findings whose path length makes the reasoning materially harder to review. A finding whose hopDepth is 3 or greater MUST include this term in addition to TRANSITIVE. |
| ARTIFACT | artifact impact | The affected entity is an artifact (source archive, lockfile, build artifact, WASM or deployment artifact). |
| CONTRACT | contract impact | The affected entity is a contract identity. Requires `affectedKinds` of CONTRACT in the finding. |
| DEPLOYMENT | deployment impact | The affected entity is a deployment record rather than the contract identity itself. The distinction matters because a contract can be re-deployed without its identity changing. |
| CHANGE | change impact | The finding is triggered by a specific typed change rather than by an inferred propagation, and MUST carry a `changeType`. Used when a diff is the input to an impact analysis. |

Enforced at: `schema/impact.schema.json/properties/impactType/items`

## Network Types

Source: `taxonomies/network-types.yaml` — openness: **open** — consumers must handle unknown terms: `true`

The network environments an Amasario observation can be made against. A network type is an Amasario classification, not a Stellar protocol fact: it groups environments that share operational semantics so a consumer can apply the right expectations about durability and availability. The Stellar network passphrase is the fact that actually identifies a Stellar network, and it is recorded separately on the network descriptor because two environments can share a passphrase while having different endpoints and retention. A consumer MUST treat an unrecognised network type as requiring explicit operator confirmation rather than assuming production safety. In particular, code that treats "not MAINNET" as "safe to mutate" is prohibited.

| Term | Label | Description |
| --- | --- | --- |
| LOCAL | local | A developer-controlled environment, typically a local Stellar Quickstart container or a standalone core instance. State is disposable, retention is not guaranteed, and a ledger boundary observed here is not meaningful evidence outside that environment. |
| FUTURENET | futurenet | A Stellar-operated environment for protocol features ahead of testnet. State can be reset without notice, so an observation here MUST record its ledger boundary and MUST NOT be treated as stable over time. |
| TESTNET | testnet | The public Stellar test network. Persistent enough for integration testing of discovery and verification, but contract state is routinely recycled and testnet identifiers carry no production meaning. |
| MAINNET | mainnet | The public Stellar production network. Observations here are the only ones with production significance, and any mutating command MUST require an explicit opt-in rather than being a default. |
| CUSTOM | custom | An operator-defined environment reachable through explicitly supplied endpoints, such as a private network, a fork, or a partner environment. The descriptor MUST supply the endpoints because Amasario does not maintain a registry of private networks. |

Enforced at: `schema/network.schema.json/properties/type`

## Relationship Types

Source: `taxonomies/relationship-types.yaml` — openness: **closed** — consumers must handle unknown terms: `false`

The exhaustive set of typed relationships that Amasario may assert between two entities. A relationship is always directed: `subject RELATIONSHIP object`, and the meaning of the arrow is fixed by this taxonomy rather than by context. Each term declares the entity kinds it may connect (`subjectTypes`, `objectTypes`) and, critically, `changePropagation`, which states which direction a change travels. Impact analysis is derived from `changePropagation`; it is never inferred from the name of the relationship.

| Term | Label | Description |
| --- | --- | --- |
| DEPENDS_ON | depends on | The subject requires the object in order to function or to be built. The requirement MUST be supported by evidence; shared naming, shared ecosystem membership or mutual mention is explicitly insufficient (see rule dependency/direct-dependency). |
| INVOCATES | invocates | The subject contract made a cross-contract call into the object contract. This relationship is only assertable from an observed transaction or invocation record; it MUST NOT be asserted from interface similarity. |
| BUILT_FROM | built from | The subject build produced the subject from the object source revision. This is the join between source provenance and build provenance. |
| DERIVED_FROM | derived from | The subject artifact was mechanically produced from the object entity (for example a WASM compiled from a build artifact, or a build artifact produced from a source archive and a lockfile). |
| DEPLOYED_AS | deployed as | Relates an executable artifact to the contract address it was deployed as, or a contract address to the deployment record that created it. Both directions are valid instances of the same relationship because the deployment record and the contract address are two observations of one event. |
| OBSERVED_IN | observed in | The subject fact was observed in the object transaction. This relationship records the provenance of an observation itself and is what allows a claim to be traced back to a verifiable ledger event. |
| VERIFIED_BY | verified by | The object entity is the entity whose digest or revision establishes the subject's provenance claim. For example a deployed WASM is VERIFIED_BY the build artifact whose digest matches it. |
| AFFECTS | affects | An explicitly declared impact edge: a change to the subject is asserted to affect the object. Unlike the dependency relationships above, this relationship is the assertion of impact itself rather than a fact from which impact is derived. |

Enforced at: `schema/dependency-edge.schema.json/properties/relationship`, `schema/graph.schema.json/$defs/edge/properties/relationship`, `schema/impact-path.schema.json/$defs/step/properties/relationship`

## Verification Statuses

Source: `taxonomies/verification-statuses.yaml` — openness: **closed** — consumers must handle unknown terms: `false`

The outcome of comparing a claim against the evidence available for it. This is deliberately independent of confidence: confidence describes how much evidence there is, verification describes what that evidence says about the claim. The distinction exists so that contradictory evidence is representable. A configuration where a claimed source revision cannot be matched to the deployed WASM MUST be reported as CONFLICTING. If the model could not express that, the only alternatives would be VERIFIED (wrong) or UNVERIFIED (lossy), and an incorrect VERIFIED is the most damaging output Amasario could produce.

| Term | Label | Description |
| --- | --- | --- |
| VERIFIED | verified | The claim is supported and the decisive evidence was checked against the claim successfully. Requires at least one evidence record that is deterministically comparable to the claim, such as a matching digest. Claiming VERIFIED without such a record is a specification violation. |
| PARTIALLY_VERIFIED | partially verified | Some but not all of the claim's components were checked successfully, and no component was contradicted. For example the source revision matched but the build toolchain identity could not be established. |
| UNVERIFIED | unverified | The claim has not been checked, or the evidence required to check it is unavailable. UNVERIFIED makes no statement about whether the claim is true. |
| CONFLICTING | conflicting | Evidence exists and contradicts the claim, or two pieces of otherwise valid evidence contradict each other. This status takes precedence over every other status: a claim with any contradicted component MUST be reported as CONFLICTING, never as VERIFIED or PARTIALLY_VERIFIED. |
| UNKNOWN | unknown | The claim could not be evaluated at all, typically because a required field was absent or because a taxonomy term in an open vocabulary was not recognised. Distinct from UNVERIFIED, which means the claim is understood but unchecked. |

Enforced at: `schema/provenance.schema.json/properties/verificationStatus`, `schema/attestation.schema.json/properties/verificationStatus`
