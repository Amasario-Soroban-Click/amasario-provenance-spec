## Contract Dependency Model

Source: `models/dependencies/contract.yaml` — concept: `DEPENDENCY_CONTRACT` — schema: `https://amasario.dev/spec/v1/schema/dependency.schema.json`

A dependency whose object is another Soroban contract. Establishing this class is where the ecosystem's most tempting shortcut lives: two contracts interacting in the same protocol does not mean one depends on the other. The model therefore admits only bases that can be checked: an observed invocation, an observed event, or an address the subject's source or storage demonstrably references. Interface similarity is admissible only at INFERRED_INTERFACE with LOW_CONFIDENCE.

| Field | Type | Requirement | Description |
| --- | --- | --- | --- |
| source | object | always | The depending contract. |
| target | object | always | The contract depended upon, identified by contract address on a named network. |
| type | string | always | Dependency class, which for this model is CONTRACT. |
| basis | string | always | How the dependency was established. OBSERVED_INVOCATION and OBSERVED_EVENT are the strongest available bases for this class. |
| evidence | array | always | Evidence supporting the dependency. For an observed invocation the evidence is the transaction and events that recorded it. |
| confidence | object | optional | How strongly the evidence supports the dependency. |
| network | object | rule | The network. Required for this class by rule dependency/contract-dependency, because a contract address identifies a contract only together with its network; the schema itself does not make it globally required, since a declared package dependency has no network. |
| firstObserved | object | optional | Earliest boundary at which the invocation or reference was observed. |
| lastObserved | object | optional | Latest boundary at which it was observed. |
| verificationStatus | string | optional | Outcome of checking the dependency's claim against its evidence. |
| metadata | object | optional | Producer-defined detail, such as the function invoked. |

**Invariants**

- A CONTRACT dependency must name a network. A contract address without a network does not identify a contract.
- A CONTRACT dependency based on INFERRED_INTERFACE must not exceed LOW_CONFIDENCE and must not appear among a report's observed facts.
- Two contracts existing in the same ecosystem, sharing an operator, or appearing in the same repository are not thereby dependent.

**Non-goals**

- This model does not claim that the target contract is reachable, live or correct at the boundary.
- This model does not assess the safety or behaviour of either contract.

## Direct Dependency Model

Source: `models/dependencies/direct.yaml` — concept: `DEPENDENCY_DIRECT` — schema: `https://amasario.dev/spec/v1/schema/dependency.schema.json`

A dependency in which the subject reaches the object with no intermediate entity. The model's purpose is to make the basis of the dependency a required, enumerated field, so that a declared dependency, a resolved dependency and an observed dependency are distinguishable rather than all presented as "depends on". This is the model that prevents Amasario implying a dependency because two projects mention each other.

| Field | Type | Requirement | Description |
| --- | --- | --- | --- |
| id | string | optional | Identifier used by relationships and reports to refer to this dependency. |
| source | object | always | The depending entity. |
| target | object | always | The entity depended upon. |
| type | string | always | Dependency class, which for this model is DIRECT. |
| basis | string | always | How the dependency was established. The field that separates evidence from speculation. |
| evidence | array | always | Evidence supporting the dependency. At least one record is required. |
| confidence | object | optional | How strongly the evidence supports the dependency. |
| network | object | optional | The network the dependency was observed on, when observed rather than declared. |
| firstObserved | object | optional | Earliest boundary at which the dependency was observed. |
| lastObserved | object | optional | Latest boundary at which the dependency was observed. |
| metadata | object | optional | Producer-defined detail such as the declaring file and line. Never used to establish, strengthen or contradict a claim. |

**Invariants**

- A dependency must carry at least one evidence record. An empty evidence set is a malformed dependency, not a weakly supported one.
- A dependency must carry a basis. There is no default, because a default basis would let an implementation silently promote a declaration into an observation.
- source and target must not be identical and of the same kind.
- lastObserved must not precede firstObserved.

**Non-goals**

- This model does not claim that a dependency is load-bearing at runtime. A declared package dependency may be unreachable code.
- This model does not claim that the target exists, only that the dependency on it is asserted with a stated basis.

## External Dependency Model

Source: `models/dependencies/external.yaml` — concept: `DEPENDENCY_EXTERNAL` — schema: `https://amasario.dev/spec/v1/schema/dependency.schema.json`

A dependency on something outside the observable Amasario boundary: a system, service or repository that can be referenced but not inspected or verified. The model exists so that the edge of the analysis is representable. Without it, a dependency on an uninspectable system would either be dropped, making the contract look self-contained, or presented like an inspected one, which is worse.

| Field | Type | Requirement | Description |
| --- | --- | --- | --- |
| source | object | always | The depending entity that references the external system. |
| target | object | always | The external entity. Its identifier is a reference, not a digest, because the content cannot be observed. |
| type | string | always | Dependency class, which for this model is EXTERNAL. |
| basis | string | always | How the dependency was established, typically CONFIGURED_ENDPOINT or DECLARED_MANIFEST. |
| evidence | array | always | Evidence supporting the dependency. For an external entity this is typically OBSERVATION evidence, which asserts presence only. |
| confidence | object | optional | Confidence in the dependency. An external dependency whose content cannot be observed should not carry high confidence about the target. |
| verificationStatus | string | optional | Outcome of checking the dependency. UNVERIFIED is expected and correct for an uninspectable target. |
| metadata | object | optional | Producer-defined detail, such as the configuration path that referenced the external system. |

**Invariants**

- An external entity must be marked as outside the observable boundary, so that being uninspectable is never mistaken for being unverified.
- An EXTERNAL dependency must not be reported as VERIFIED, because verification requires content that a boundary excludes.
- The boundary must be stated on the relationship, so a consumer can tell why the dependency was not followed further.

**Non-goals**

- This model does not attempt to inspect external systems.
- This model does not claim that an external dependency is unavailable, untrustworthy or unsafe merely because it is out of boundary.

## Package Dependency Model

Source: `models/dependencies/package.yaml` — concept: `DEPENDENCY_PACKAGE` — schema: `https://amasario.dev/spec/v1/schema/dependency.schema.json`

A dependency whose object is a software package or crate. The model insists on a distinction that most tooling blurs: a declared dependency and a resolved dependency are different facts. A manifest says what the author asked for; a lockfile says what was actually compiled. Only the second can support a claim about a deployed artifact.

| Field | Type | Requirement | Description |
| --- | --- | --- | --- |
| source | object | always | The depending entity, typically a SOURCE or BUILD entity. |
| target | object | always | The package depended upon, identified by name and resolved version where available. |
| type | string | always | Dependency class, which for this model is PACKAGE. |
| basis | string | always | Whether the dependency was DECLARED_MANIFEST or RESOLVED_LOCKFILE. The two must not be conflated. |
| evidence | array | always | Evidence supporting the dependency. A resolved dependency is evidenced by the lockfile artifact. |
| confidence | object | optional | How strongly the evidence supports the dependency. |
| verificationStatus | string | optional | Outcome of checking the dependency against its evidence. |
| metadata | object | optional | Producer-defined detail, such as the manifest name, or the declared version requirement as distinct from the resolved version. |

**Invariants**

- A PACKAGE dependency must record whether its basis is declaration or resolution. A declared dependency must not be presented as resolved.
- A declared version requirement and a resolved version must be recorded separately when both are known; collapsing them hides the resolution step.
- A package must be identified by more than a name where a resolved version or digest is available, because names are not unique across ecosystems.

**Non-goals**

- This model does not claim that a resolved package is reachable from the compiled artifact. A dependency may be resolved and never used.
- This model does not assess whether a package or version is malicious, deprecated or well maintained.

## Runtime Dependency Model

Source: `models/dependencies/runtime.yaml` — concept: `DEPENDENCY_RUNTIME` — schema: `https://amasario.dev/spec/v1/schema/dependency.schema.json`

A dependency that exists only while the subject executes, observed from a transaction and its events. The model exists because runtime dependencies are the ones operators actually care about during an incident, and equally because they are unobservable from source: an implementation that never observed an invocation must report that it did not, rather than guessing from an interface.

| Field | Type | Requirement | Description |
| --- | --- | --- | --- |
| source | object | always | The contract that performed the invocation. |
| target | object | always | The contract invoked. |
| type | string | always | Dependency class, which for this model is RUNTIME. |
| basis | string | always | How the dependency was established. For this class the basis is OBSERVED_INVOCATION or OBSERVED_EVENT. |
| evidence | array | always | Evidence supporting the dependency, invariably a transaction and its events. |
| network | object | rule | The network the invocation was observed on. Required for this class by rule dependency/direct-dependency, because an invocation observation is meaningful only relative to a network. |
| firstObserved | object | rule | The boundary at which the invocation was first observed. Required for this class by rule dependency/direct-dependency, since for a runtime dependency an observation is the only thing that establishes it. |
| lastObserved | object | optional | Latest boundary at which the invocation was observed. |
| confidence | object | optional | How strongly the evidence supports the dependency. |
| metadata | object | optional | Producer-defined detail, such as the invoked function or the invocation depth. |

**Invariants**

- A RUNTIME dependency must be established from an observed transaction or event. It must never be inferred from source alone, because source does not determine what executes.
- Evidence for a RUNTIME dependency must come from a successful transaction. An invocation recorded in a failed transaction did not take effect and cannot support the dependency.
- A RUNTIME dependency observed once must be reported as observed once, not as a permanent property of the contract.

**Non-goals**

- This model does not claim that an unobserved invocation never happens. A bounded observation window supports only what it observed.
- This model does not claim that a runtime dependency is a security risk. It records that a call occurred.

## Transitive Dependency Model

Source: `models/dependencies/transitive.yaml` — concept: `DEPENDENCY_TRANSITIVE` — schema: `https://amasario.dev/spec/v1/schema/dependency.schema.json`

A dependency the subject reaches only through one or more intermediate entities. The model requires the intermediate path to be recorded, because a transitive edge without its path is indistinguishable from a guess: a consumer cannot tell whether the analysis walked a real chain or collapsed several uncertain hops into one confident-looking statement.

| Field | Type | Requirement | Description |
| --- | --- | --- | --- |
| id | string | optional | Identifier used by relationships and reports to refer to this dependency. |
| source | object | always | The depending entity, which does not depend on the target directly. |
| target | object | always | The entity reached through the path. |
| type | string | always | Dependency class, which for this model is TRANSITIVE. |
| basis | string | always | How the dependency was established. A transitive dependency resolved from a lockfile is still established from resolution, not from observation. |
| evidence | array | always | Evidence for the whole dependency, in addition to the per-hop evidence the path must carry. |
| path | array | rule | The intermediate entities between source and target, in order. Required for TRANSITIVE by rule dependency/transitive-dependency. |
| confidence | object | optional | Aggregated confidence across the path, computed as the minimum ordinal so the chain is not stronger than its weakest hop. |
| firstObserved | object | optional | Earliest boundary at which the dependency was observed. |
| lastObserved | object | optional | Latest boundary at which the dependency was observed. |
| metadata | object | optional | Producer-defined detail. Never used to establish, strengthen or contradict a claim. |

**Invariants**

- A TRANSITIVE dependency must carry a non-empty path.
- Aggregated confidence must equal the minimum ordinal of the hops, so a transitive claim can never be stronger than the weakest step in it.

**Non-goals**

- This model does not claim that a transitive dependency is transitive at runtime. Reachability through build inputs and reachability through invocation are different and are distinguished by the path's relationship types.
- This model does not assert that the path found is the only path between the two entities.

## WASM Dependency Model

Source: `models/dependencies/wasm.yaml` — concept: `DEPENDENCY_WASM` — schema: `https://amasario.dev/spec/v1/schema/dependency.schema.json`

A dependency whose object is a WebAssembly artifact that the subject embeds, references or was derived from. Identity for this class is a digest and nothing else: a module is identical to another module when their content hashes match, and no amount of metadata similarity establishes a relationship between two modules.

| Field | Type | Requirement | Description |
| --- | --- | --- | --- |
| source | object | always | The depending entity, typically a BUILD, ARTIFACT or CONTRACT entity. |
| target | object | always | The WASM artifact depended upon, identified by content digest. |
| type | string | always | Dependency class, which for this model is WASM. |
| basis | string | always | How the dependency was established. EMBEDDED_DIGEST is the strongest basis for this class, because a digest match is recomputable. |
| evidence | array | always | Evidence supporting the dependency. For an embedded module, the evidence is the artifact record carrying the matching digest. |
| confidence | object | optional | How strongly the evidence supports the dependency. |
| network | object | optional | The network, when the module was observed as a deployed executable rather than as a build input. |
| metadata | object | optional | Producer-defined detail, such as the importing module name. Never used to establish the dependency. |

**Invariants**

- A WASM dependency must be established from a digest match or from an explicit build input. Size, module name and metadata similarity are not bases.
- A WASM artifact's digest must use sha256, the algorithm permitted for that artifact type.
- Two modules with equal digests are the same artifact; two modules with different digests must not be treated as versions of one another unless a build input establishes the derivation.

**Non-goals**

- This model does not disassemble, decompile or analyse module content.
- This model does not claim that an embedded module is invoked at runtime.

## Artifact Evidence Model

Source: `models/evidence/artifact.yaml` — concept: `EVIDENCE_ARTIFACT` — schema: `https://amasario.dev/spec/v1/schema/evidence.schema.json`

Evidence about an artifact's existence and identity. The model requires the artifact class alongside the digest, because a digest is a function of bytes and the same bytes are different things depending on what they are claimed to be: a digest with no type cannot tell a reader whether it identifies source, a lockfile or an executable.

| Field | Type | Requirement | Description |
| --- | --- | --- | --- |
| id | string | always | Evidence identifier, referenced by every claim relying on this record. |
| type | string | always | Evidence class, which for this model is ARTIFACT. |
| claim | string | always | The exact claim this record supports, for example that a named digest is the digest of a named artifact. |
| observedAt | string | always | When this record was observed. |
| artifactType | string | conditional | The artifact class the digest was computed over. Required for ARTIFACT evidence. |
| digest | object | conditional | The digest. Required for ARTIFACT evidence. |
| boundary | object | optional | Observation boundary, where the artifact was obtained from a network rather than locally. |
| supportsRelationships | array | optional | Identifiers of the relationships this evidence is scoped to. |

**Invariants**

- An ARTIFACT evidence record must carry both artifactType and digest.
- The digest algorithm must be one permitted for the declared artifact type.
- The claim must identify the artifact, not merely state that a digest exists.

**Non-goals**

- This model does not assert that an artifact is the one a producer claimed to have published, only that the record addresses specific content.
- This model does not assess artifact content.

## Attestation Evidence Model

Source: `models/evidence/attestation.yaml` — concept: `EVIDENCE_ATTESTATION` — schema: `https://amasario.dev/spec/v1/schema/evidence.schema.json`

Evidence that a statement was made by an identified issuer. This model is the boundary between Amasario and the organisations that operate alongside it: an attestation is evidence about a claim, never a property of the thing the claim concerns. A build attestation therefore says that someone attested to a build, and says nothing about the contract that build produced.

| Field | Type | Requirement | Description |
| --- | --- | --- | --- |
| id | string | always | Evidence identifier, referenced by every claim relying on this record. |
| type | string | always | Evidence class, which for this model is ATTESTATION. |
| claim | string | always | The exact claim this record supports. Must be no broader than the claim the issuer actually made. |
| observedAt | string | always | When Amasario observed the attestation, which is distinct from when the issuer issued it. |
| attestationId | string | conditional | The identifier of the attestation record this evidence refers to. Required for ATTESTATION evidence, because evidence pointing at nothing is not evidence. |
| digest | object | optional | Digest over the attestation's canonical form, so the exact attested claim can be reconstructed. |
| boundary | object | optional | Observation boundary, where the attestation was retrieved from a network or service. |
| supportsRelationships | array | optional | Identifiers of the relationships this evidence is scoped to. |

**Invariants**

- An ATTESTATION evidence record must name the attestation it refers to.
- An attestation whose signature was not checked must be recorded as UNVERIFIED, and the accompanying attestation record must state what checking, if any, was performed.
- An attestation must not be used to widen a claim beyond its stated scope. A build attestation cannot support a claim about behaviour, correctness or safety.

**Non-goals**

- This model does not establish that an issuer is competent, independent or acting in good faith.
- This model does not treat an attestation as a property of an artifact. Attestations are referenced by the claims they support, never embedded as flags.

## Build Evidence Model

Source: `models/evidence/build.yaml` — concept: `EVIDENCE_BUILD` — schema: `https://amasario.dev/spec/v1/schema/evidence.schema.json`

Evidence about how an artifact was produced. The model requires both a toolchain identity and a configuration digest, because either alone is insufficient to re-run a build: the same source compiled by a different toolchain version, or with different flags, produces different output. Two of the three inputs to a build is not enough to establish anything about its result.

| Field | Type | Requirement | Description |
| --- | --- | --- | --- |
| id | string | always | Evidence identifier, referenced by every claim relying on this record. |
| type | string | always | Evidence class, which for this model is BUILD. |
| claim | string | always | The exact claim this record supports. |
| observedAt | string | always | When this record was observed. |
| toolchain | string | conditional | The toolchain identity the build used. Required for BUILD evidence. |
| configurationDigest | object | conditional | Digest of the build configuration. Required for BUILD evidence, because a configuration that cannot be compared cannot be re-used. |
| digest | object | optional | Digest over the produced artifact, when this record is what establishes it. |
| boundary | object | optional | Observation boundary, where the build evidence was collected from a remote service. |
| supportsRelationships | array | optional | Identifiers of the relationships this evidence is scoped to. |

**Invariants**

- A BUILD evidence record must carry both toolchain and configurationDigest. A record naming only one cannot support a reproducibility claim.
- The toolchain identity must be an exact version, not a range or a floating channel.

**Non-goals**

- This model does not execute or re-execute builds.
- This model does not assert that a build is trustworthy because its provenance is recorded.

## Event Evidence Model

Source: `models/evidence/event.yaml` — concept: `EVIDENCE_EVENT` — schema: `https://amasario.dev/spec/v1/schema/evidence.schema.json`

Evidence from a contract event emitted during execution. Events are the primary observable for cross-contract invocation, which makes this class the backbone of runtime dependency discovery, and also the class most easily over-read: an event shows that something happened, not why or with what effect. The model therefore keeps the emitting contract, the transaction and the ledger mandatory together.

| Field | Type | Requirement | Description |
| --- | --- | --- | --- |
| id | string | always | Evidence identifier, referenced by every claim relying on this record. |
| type | string | always | Evidence class, which for this model is EVENT. |
| claim | string | always | The exact claim this record supports. |
| observedAt | string | always | When this record was observed. |
| contractId | string | conditional | The emitting contract address. Required for EVENT evidence. |
| transactionHash | string | conditional | The transaction whose execution emitted the event. Required for EVENT evidence. |
| ledger | integer | conditional | The ledger the emitting transaction was included in. Required for EVENT evidence. |
| boundary | object | conditional | Observation boundary. Required for EVENT evidence. |
| digest | object | optional | Digest over the event payload, so a change to the payload the analysis depended on can be detected without storing contract-defined data. |
| supportsRelationships | array | optional | Identifiers of the relationships this evidence is scoped to. |

**Invariants**

- An EVENT evidence record must carry contractId, transactionHash, ledger and boundary.
- An event emitted during a transaction recorded as unsuccessful must not be cited as evidence that the effect it describes occurred.
- Event payloads must not be modelled beyond a digest, because their encoding is contract-defined and guessing it would invent semantics.

**Non-goals**

- This model does not interpret contract-defined event payloads.
- This model does not assert that an event's name reflects the effect it describes.

## Source Evidence Model

Source: `models/evidence/source.yaml` — concept: `EVIDENCE_SOURCE` — schema: `https://amasario.dev/spec/v1/schema/evidence.schema.json`

Evidence about a source repository, revision or archive. The model requires the repository and revision together, because evidence traceable only to a repository is not traceable at all: a repository changes continuously, so a reader cannot revisit the state the claim was made about without knowing the revision.

| Field | Type | Requirement | Description |

| claim | string | always | The exact claim this record supports. Required so a reader can decide whether it bears on the claim. |

| repository | string | conditional | The repository the revision was read from. Required for SOURCE evidence. |
| revision | string | conditional | The exact revision observed. Required for SOURCE evidence. |

- A SOURCE evidence record must carry both repository and revision. Evidence carrying only a repository cannot be revisited.
- The claim must state what is being asserted about the revision, not merely that a revision exists.

- This model does not retain source content.

## Transaction Evidence Model

Source: `models/evidence/transaction.yaml` — concept: `EVIDENCE_TRANSACTION` — schema: `https://amasario.dev/spec/v1/schema/evidence.schema.json`

Evidence from a ledger transaction. This is the strongest evidence class Amasario has for what happened on a network, and the model makes the success flag mandatory for that reason: a transaction is evidence of an attempt, and whether its intended effect occurred is a separate fact that nothing else in the evidence set can recover.

| Field | Type | Requirement | Description |
| --- | --- | --- | --- |
| id | string | always | Evidence identifier, referenced by every claim relying on this record. |
| type | string | always | Evidence class, which for this model is TRANSACTION. |
| claim | string | always | The exact claim this record supports. For a transaction, the claim must state the effect being evidenced rather than restating the transaction's existence. |
| observedAt | string | always | When this record was observed. |
| transactionHash | string | conditional | The transaction hash. Required for TRANSACTION evidence. |
| ledger | integer | conditional | The ledger the transaction was included in. Required for TRANSACTION evidence. |
| successful | boolean | conditional | Whether the transaction succeeded. Required for TRANSACTION evidence, and the reason this class cannot be reduced to a hash and a ledger. |
| boundary | object | conditional | Observation boundary. Required for TRANSACTION evidence. |
| supportsRelationships | array | optional | Identifiers of the relationships this evidence is scoped to. |

**Invariants**

- A TRANSACTION evidence record must carry transactionHash, ledger, successful and boundary.
- A record with successful set to false must not be cited as evidence that its intended effect occurred. A rule enforces this rather than leaving it to interpretation.
- The claim must describe what the transaction established, not merely that it exists.

**Non-goals**

- This model does not assert that a successful transaction achieved a particular intent, only that the network recorded it as successful.
- This model does not attempt to determine whether a transaction was submitted by the party that benefits from it.

## Affected Artifact Model

Source: `models/impact/affected-artifact.yaml` — concept: `IMPACT_AFFECTED_ARTIFACT` — schema: `https://amasario.dev/spec/v1/schema/impact.schema.json`

A finding whose affected entity is an artifact or an executable. This is the impact class that answers the question a consumer most needs before an upgrade: if a build input or a source revision changes, which deployed executables no longer correspond to their claimed provenance. It is deliberately about correspondence rather than correctness, because a digest mismatch is a checkable fact and a broken contract is not.

| Field | Type | Requirement | Description |
| --- | --- | --- | --- |
| id | string | always | Finding identifier, stable across runs. |
| changedEntity | object | always | The entity that changed, typically a SOURCE, BUILD or ARTIFACT entity. |
| affectedEntity | object | always | The affected artifact or executable, identified by digest. |
| impactType | array | always | Classifications of the finding. For this model the set must include ARTIFACT when the affected entity is an ARTIFACT or WASM node. |
| hopDepth | integer | always | Number of edges between the entities. |
| evidence | array | always | Evidence supporting the finding. |
| confidence | object | always | Confidence for the finding. |
| reason | string | always | Why the artifact is considered affected, stated in terms of the traversed derivations. |
| path | object | rule | The path from the changed entity. Required when hopDepth is greater than zero. |
| direction | string | optional | Which way the change propagated. |
| changeType | string | rule | The kind of change that triggered the finding. Required when impactType includes CHANGE. |
| verificationState | string | optional | Whether the relied-upon relationships were verified. |
| boundary | object | optional | Observation boundary the finding was computed at. |
| truncated | boolean | optional | Whether propagation was bounded before exhaustion. |

**Invariants**

- impactType must include ARTIFACT when the affected entity is an artifact or executable.
- changeType must be present when impactType includes CHANGE.
- The finding must not assert that an artifact is broken or invalid, only that it may no longer correspond to the provenance it was recorded with.

**Non-goals**

- This model does not claim that a changed input produced a different output. That requires the output's digest to be recomputed, which is a verification step rather than an impact step.
- This model does not rank artifacts by importance.

## Affected Contract Model

Source: `models/impact/affected-contract.yaml` — concept: `IMPACT_AFFECTED_CONTRACT` — schema: `https://amasario.dev/spec/v1/schema/impact.schema.json`

A finding whose affected entity is a contract identity. The distinction this model enforces is between a contract and the executable it hosts: a re-deployment changes what an address runs without necessarily changing the artifact a consumer depends on, and a dependency on a contract is a dependency on a mutable thing. Findings about contracts therefore carry the identity version they were computed against.

| Field | Type | Requirement | Description |
| --- | --- | --- | --- |
| id | string | always | Finding identifier, stable across runs. |
| changedEntity | object | always | The entity that changed. |
| affectedEntity | object | always | The affected contract identity. Its identity version is part of what the finding was computed against. |
| impactType | array | always | Classifications of the finding. For this model the set must include CONTRACT. |
| hopDepth | integer | always | Number of edges between the entities. |
| evidence | array | always | Evidence supporting the finding. |
| confidence | object | always | Confidence for the finding. |
| reason | string | always | Why the contract is considered affected, stated in terms of the relationships traversed. |
| path | object | rule | The path from the changed entity. Required when hopDepth is greater than zero. |
| direction | string | optional | Which way the change propagated. A change to a contract propagates to its dependents, not to the contracts it depends on, unless an AFFECTS edge says otherwise. |
| verificationState | string | optional | Whether the relied-upon relationships were verified. |
| boundary | object | optional | Observation boundary the finding was computed at. |
| truncated | boolean | optional | Whether propagation was bounded before exhaustion. |

**Invariants**

- impactType must include CONTRACT whenever the affected entity's kind is CONTRACT.
- The finding must be computed against a specific contract identity version, because an address can host different executables over time.
- A contract that merely shares a network, operator or repository with the changed entity must not be reported as affected.

**Non-goals**

- This model does not claim that an affected contract will fail, only that a change may reach it.
- This model does not assess the affected contract's behaviour, correctness or safety.

## Affected Deployment Model

Source: `models/impact/affected-deployment.yaml` — concept: `IMPACT_AFFECTED_DEPLOYMENT` — schema: `https://amasario.dev/spec/v1/schema/impact.schema.json`

A finding whose affected entity is a deployment record rather than a contract identity. The distinction matters operationally: a deployment finding says that what currently sits at an address no longer matches the state the analysis was computed against, whereas a contract finding says that a contract is in the blast radius. Different remediation follows, so conflating them would make the output unusable for the workflow it exists to support.

| Field | Type | Requirement | Description |
| --- | --- | --- | --- |
| id | string | always | Finding identifier, stable across runs. |
| changedEntity | object | always | The entity that changed, typically a WASM or ARTIFACT entity. |
| affectedEntity | object | always | The affected deployment record, identified by its contract and the ledger it was recorded at. |
| impactType | array | always | Classifications of the finding. For this model the set must include DEPLOYMENT. |
| hopDepth | integer | always | Number of edges between the entities. |
| evidence | array | always | Evidence supporting the finding. |
| confidence | object | always | Confidence for the finding. |
| reason | string | always | Why the deployment is considered affected, stated in terms of the traversed relationships. |
| path | object | rule | The path from the changed entity, typically a DEPLOYED_AS hop followed by further propagation. Required when hopDepth is greater than zero. |
| direction | string | optional | Which way the change propagated. A change to the deployment propagates to the executable it hosts, not the reverse. |
| verificationState | string | optional | Whether the relied-upon relationships were verified. |
| boundary | object | optional | Observation boundary the finding was computed at. |
| truncated | boolean | optional | Whether propagation was bounded before exhaustion. |

**Invariants**

- impactType must include DEPLOYMENT when the affected entity is a deployment rather than a contract identity.
- A finding about a deployment must identify the ledger the deployment was recorded at, because a contract can be deployed to more than once.
- An UNCONFIRMED or FAILED deployment must not be reported as an affected deployment of a change, since no successful deployment is being affected.

**Non-goals**

- This model does not claim that a deployment should be rolled back, replaced or re-verified.
- This model does not assert that a deployment is currently the effective state of a contract beyond the observation boundary.

## Direct Impact Model

Source: `models/impact/direct.yaml` — concept: `IMPACT_DIRECT` — schema: `https://amasario.dev/spec/v1/schema/impact.schema.json`

A finding in which a change to one entity reaches another in a single hop. One hop is the depth at which a finding is easiest to check and easiest to overstate, so the model requires the path, the evidence and a reason in terms of the traversed relationship rather than a score.

| Field | Type | Requirement | Description |
| --- | --- | --- | --- |
| id | string | always | Finding identifier, stable across runs so a diff can tell a new finding from a reordering. |
| changedEntity | object | always | The entity that changed or is assumed to change. |
| affectedEntity | object | always | The entity potentially affected. |
| impactType | array | always | Classifications of the finding. For this model the set must include DIRECT. |
| hopDepth | integer | always | Number of edges between the entities. Exactly 1 for this model. |
| evidence | array | always | Evidence supporting the finding. Required and non-empty. |
| confidence | object | always | Confidence, derived from the evidence. |
| reason | string | always | Why the entity is considered affected, stated in terms of the relationship traversed. This is what replaces a score. |
| path | object | rule | The path from changed to affected entity. Required by rule impact/direct-impact whenever hopDepth is greater than zero. |
| relationshipTypes | array | optional | The relationships traversed, in path order. |
| direction | string | optional | Which way the change propagated, derived from the relationship's changePropagation. |
| verificationState | string | optional | Whether the relationships the finding relies on were themselves verified. |
| truncated | boolean | optional | Whether propagation was bounded before exhaustion. |

**Invariants**

- hopDepth must be exactly 1 and impactType must include DIRECT.
- The single traversed relationship must have a changePropagation of object_to_subject or subject_to_object. An impact finding must never rest on OBSERVED_IN or VERIFIED_BY, whose propagation is none.
- The reason must name the relationship traversed, so a reader can check the hop rather than trusting the depth.

**Non-goals**

- This model does not claim that the affected entity is broken. It claims that a change may affect it, with the reasoning shown.
- This model does not compute a severity or risk score.

## Transitive Impact Model

Source: `models/impact/transitive.yaml` — concept: `IMPACT_TRANSITIVE` — schema: `https://amasario.dev/spec/v1/schema/impact.schema.json`

A finding in which a change reaches an entity through two or more hops. The model exists because transitive findings are where impact analysis most easily becomes untrustworthy: each extra hop multiplies the number of claims a reader would have to check by hand, so the model requires the full path with per-step evidence and fixes the confidence to the weakest step rather than the best.

| Field | Type | Requirement | Description |
| --- | --- | --- | --- |
| id | string | always | Finding identifier, stable across runs. |
| changedEntity | object | always | The entity that changed or is assumed to change. |
| affectedEntity | object | always | The entity potentially affected. |
| impactType | array | always | Classifications of the finding. For this model the set must include TRANSITIVE, and MULTI_HOP when the depth is three or more. |
| hopDepth | integer | always | Number of edges between the entities. Two or more for this model. |
| path | object | rule | The full path, with per-step evidence. Required by rule impact/transitive-impact, and the reason transitive findings stay auditable. |
| relationshipTypes | array | optional | The relationships traversed, in path order. Must agree with the path. |
| direction | string | optional | Which way the change propagated. Both directions may be followed in one analysis, which is why the field records which was used. |
| evidence | array | always | Evidence supporting the finding as a whole, in addition to the per-step evidence the path must carry. |
| confidence | object | always | Confidence for the whole finding, computed as the minimum ordinal across the steps. |
| reason | string | always | Why the entity is considered affected, stated in terms of the traversed relationships. |
| verificationState | string | optional | Whether the relationships relied upon were verified. |
| boundary | object | optional | Observation boundary the finding was computed at. |
| truncated | boolean | optional | Whether propagation was bounded before exhaustion. |

**Invariants**

- hopDepth must be at least 2, impactType must include TRANSITIVE, and MULTI_HOP must additionally be present when hopDepth is 3 or greater.
- Every step in the path must carry its own evidence.
- The aggregated confidence must be the minimum ordinal across the steps, so a transitive finding can never be stronger than its weakest hop.
- No step may traverse a relationship whose changePropagation is none.

**Non-goals**

- This model does not claim that all reachable entities are affected, only those the traversal found within the configured bound.
- This model does not claim to have found every path between the entities, and does not enumerate alternative paths as if it had.

## Artifact Model

Source: `models/provenance/artifact.yaml` — concept: `ARTIFACT` — schema: `https://amasario.dev/spec/v1/schema/artifact.schema.json`

A content-addressable object participating in provenance. The model is built around one requirement: an artifact that is not addressed by a digest cannot have identity, and every claim about it would therefore be unfalsifiable. Derivations are modelled as a set of inputs rather than a chain, because a real build has several inputs and collapsing them loses the information that verification needs.

| Field | Type | Requirement | Description |
| --- | --- | --- | --- |
| id | string | always | Unique identifier within the producing document. |
| type | string | always | The artifact class, constrained to artifact-types. |
| digest | object | always | The content digest. Required for every artifact type. |
| sizeBytes | integer | optional | Artifact size, used as a cheap drift check against a digest. |
| mediaType | string | optional | IANA media type. Informational, never used for matching. |
| locator | string | optional | Where the artifact was retrieved from, so evidence can be revisited. Never treated as identity. |
| parent | object | optional | The single artifact this was derived from, for one-to-one derivations. |
| inputs | array | optional | Every input that contributed to this artifact, for many-to-one derivations. |
| derived | array | optional | Artifacts directly produced from this one. |
| reproducible | string | optional | Whether this artifact's digest reproduces from the same inputs and configuration. |

**Invariants**

- A WASM artifact must be digested with sha256, the algorithm permitted for that type and the one the Stellar network uses to report a contract's executable hash.
- An artifact must appear in at most one parent relationship; several contributing inputs are expressed through inputs.
- An artifact's digest algorithm must be one permitted for its type.

**Non-goals**

- This model does not store, host or transfer artifact content. It addresses content; it does not hold it.
- This model does not assert that two artifacts with equal digests are the same file, only that they have equal content.

## Build Provenance Model

Source: `models/provenance/build.yaml` — concept: `BUILD` — schema: `https://amasario.dev/spec/v1/schema/build.schema.json`

How an artifact was produced from source. Build provenance is what turns an unverifiable claim into a checkable one, but only when the inputs are recorded precisely enough to be re-run. This model therefore requires exact toolchain versions and rejects floating channels, and it distinguishes a build that was shown not to reproduce from one where reproduction was never attempted.

| Field | Type | Requirement | Description |
| --- | --- | --- | --- |
| sourceRevision | string | always | The source revision this build consumed. |
| toolchain | object | optional | Compiler and toolchain identity, with an exact version rather than a range. |
| configuration | object | optional | Build configuration as resolvable values plus a digest over the whole, so two configurations are comparable without modelling every toolchain. |
| lockfile | object | optional | The dependency lock information the build resolved against. A declared dependency set does not determine what was compiled; the lockfile does. |
| target | string | optional | The artifact kind this build was expected to produce. |
| artifact | object | optional | The artifact this build produced. |
| artifactDigest | object | optional | Digest of the produced artifact, repeated at this level so a build stays comparable if its artifact record is lost. |
| reproducibility | string | optional | What is known about whether this build reproduces. |
| attestations | array | optional | Identifiers of attestations referring to this build. Referenced rather than embedded, because an attestation is evidence about a claim and not a property of the build. |

**Invariants**

- A toolchain version must be exact. A version range or a floating release channel is not acceptable, because it cannot distinguish two builds that produced different output.
- configuration.digest must be present whenever configuration is present, so that two configurations can be compared without interpretation.
- reproducibility must not be set to NOT_REPRODUCED when the question was not attempted; NOT_ATTEMPTED exists for that case.

**Non-goals**

- This model does not execute builds. It records what a build declared and what it produced.
- This model does not assert that a build is trustworthy because it is reproducible. Reproducibility establishes that a digest corresponds to a source revision, nothing further.

## Contract Identity Model

Source: `models/provenance/contract.yaml` — concept: `CONTRACT` — schema: `https://amasario.dev/spec/v1/schema/contract.schema.json`

The canonical identity of a Soroban contract. This model exists because the question "which contract is this?" has no single-field answer: an address is unique only within a network, and an address can host different executables over time as it is upgraded. Complete identity therefore requires an address, a network, an executable and an identity version together.

| Field | Type | Requirement | Description |
| --- | --- | --- | --- |
| contractId | string | always | The strkey-encoded contract address. |
| network | object | always | The network the identity was observed on. Required because a contract address is only unique within a network. |
| identityVersion | integer | always | Version of this identity record. Increments whenever any identity-defining field changes. |
| wasmHash | object | optional | Hash of the executable hosted at this identity version. Without it an address establishes no provenance. |
| ledgerSequence | integer | optional | The ledger at which this identity was most recently established. |
| firstObservedLedger | integer | optional | Earliest ledger at which this address was observed to exist. |
| lastObservedLedger | integer | optional | Latest ledger at which this identity was observed to hold. |
| deploymentTransaction | string | optional | Hash of the transaction that created the contract, when identified. |
| deploymentOperation | integer | optional | Zero-based operation index of the deployment within its transaction. |
| executableType | string | optional | The kind of executable behind the address, so a Stellar Asset Contract is not forced to have a WASM hash. |

**Invariants**

- lastObservedLedger must not be less than firstObservedLedger.
- A contract whose executableType is STELLAR_ASSET must not carry a wasmHash, because a built-in executable has no user-uploaded module.
- identityVersion must be at least 1, and two records with the same contractId and different identityVersion are different identities rather than conflicting observations of one.

**Non-goals**

- This model does not claim ownership, authorship or control of a contract. The deploying account is an observation about who submitted a transaction, not a claim about who operates the contract.
- This model does not assert that a contract is current or active beyond the recorded observation boundary.
- This model does not resolve the true creation ledger of a contract, only the earliest ledger at which an implementation observed it.

## Deployment Model

Source: `models/provenance/deployment.yaml` — concept: `DEPLOYMENT` — schema: `https://amasario.dev/spec/v1/schema/deployment.schema.json`

The record of an executable becoming a contract. This model exists because the deployed artifact, the deployment event and the resulting contract are three different things that are routinely conflated, and conflating them hides the cases that matter: an upload that was never instantiated, an upgrade that left the address unchanged, and a deployment whose transaction failed.

| Field | Type | Requirement | Description |
| --- | --- | --- | --- |
| contractId | string | always | The contract address this deployment concerns. |
| network | object | always | The network the deployment was observed on. |
| status | string | always | What is known about this deployment, constrained to deployment-statuses. |
| transaction | object | optional | The transaction that carried the deployment. |
| ledger | integer | optional | The ledger the deployment transaction was included in. |
| operation | integer | optional | Zero-based index of the deploying operation within its transaction. |
| wasmHash | object | optional | Hash of the executable deployed, kept alongside the contract's current hash so a deployment stays analysable after an upgrade. |
| deploymentArtifact | object | optional | The artifact uploaded as part of this deployment, when the upload was observable. |
| deployer | string | optional | The account that signed the deployment. An observation about who submitted the transaction, never a claim about ownership. |
| upgradeOf | object | optional | The previous executable hash when this was an upgrade. Absent means the question was not answered. |

**Invariants**

- status must be CONFIRMED only when the deployment is evidenced as successful and the resulting contract is reported by the network at the boundary. A transaction recorded as unsuccessful cannot support CONFIRMED.
- ledger must be present whenever transaction is present, because a transaction cannot be located again without knowing which ledger contains it.
- UNCONFIRMED must not be used to mean FAILED. An unknown outcome and a negative outcome are different states.

**Non-goals**

- This model does not judge whether a deployment was appropriate, authorised or desirable.
- This model does not assert that a contract is currently reachable merely because its deployment is confirmed.

## Source Provenance Model

Source: `models/provenance/source.yaml` — concept: `SOURCE` — schema: `https://amasario.dev/spec/v1/schema/source.schema.json`

Where the source of a deployed artifact is claimed to have come from. The model separates what can be checked from what can only be read: a revision digest is a fact that can be recomputed, whereas a repository URL and a branch name are references that can change underneath it. Source provenance is the weakest link in most real chains, so this model is explicit about which part is carrying the weight.

| Field | Type | Requirement | Description |
| --- | --- | --- | --- |
| repositoryUrl | string | always | Canonical URL of the source repository. |
| revision | string | always | The exact source revision. Only a hex digest revision can support a VERIFIED status. |
| repositoryName | string | optional | Human-readable name, for reporting only. Never used for matching. |
| ref | object | optional | The mutable reference the revision was resolved from, recorded so it is visible that the revision was reached through a mutable name. |
| artifactDigest | object | optional | Digest of the source archive, which covers packaging as well as content and therefore establishes something different from the revision. |
| timestamp | string | optional | Timestamp the source host reports for the revision. An observation about the host's record, not a proof of authorship timing. |
| license | string | optional | Declared licence metadata. Amasario does not assess licence compatibility. |
| buildRelationship | string | optional | How this source relates to the build that consumed it. |

**Invariants**

- A revision reached through a branch or tag ref must not by itself support VERIFIED provenance, because the ref can be moved after the analysis.
- repositoryName must never be used to establish a relationship. Two repositories with the same name are not thereby related.

**Non-goals**

- This model does not read, fetch or archive source code. It records references and digests so that a consumer can do so if it chooses.
- This model does not claim that a revision is the only revision from which a deployed artifact could have been built.
